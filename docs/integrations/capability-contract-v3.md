# Capability Contract v3 — Catalog-first review candidate

Base branch: `feat/universal-api-capabilities`, base commit
`f0b6d2f7b7305fe95300e6676abadb0751e57ef7`.
This change is a local review candidate; it is not a release or a live-provider certification.

## User-visible behavior and cost

| Action | Network/model behavior |
| --- | --- |
| Load capability configuration | Pure local catalog + cached metadata + scoped evidence; no SDK client required, no model generation, no API key required. |
| Get model list | One models-list HTTP call, no generation, no automatic model selection. A missing endpoint is not a reason to call chat. |
| Test connection | One models-list HTTP call, 5-second SDK I/O timeout, retries disabled. Missing list support is `unverified`, not a false successful chat test. |
| Edit/save/reload settings | No model generation. |
| Verify current value / one capability / chat | Confirmation required; at most one SDK completion call, retries disabled, no negative controls, enumeration, preflight or fallback. |
| Ordinary application work | The existing business request only; local observation adds no model request. |

`GET /models` establishes list-endpoint access, not current-model generation rights. Network operations still depend on DNS, proxies and the endpoint; the SDK timeout is an I/O timeout, not a total wall-clock guarantee. Zero generation means no inference tokens generated by this client; external gateways may have their own non-token billing policies.

Verification asks for a maximum of 64 completion tokens and an 8-second SDK I/O timeout. Compatible services may count reasoning differently or ignore limits; this is not an absolute monetary cap. Verifying a larger output-token limit is refused locally. Change that limit for normal work instead. The interface shows a fee confirmation and sends no request when it is cancelled.

The former `quick` API mode now resolves locally. The former `deep` mode fails before I/O with a migration message. The normal interface no longer offers batch scanning. `model_runtime/probes.py` now registers bounded single-capability fixtures, not a model/parameter allowlist. No background model calls occur when a control is changed.

## Domain, evidence, hint and selection are distinct

Example (illustrative schema, not a universal model claim):

```json
{
  "type": "number",
  "status": "supported",
  "source": "catalog",
  "domain": {
    "minimum": 0,
    "maximum": 2,
    "source": "catalog",
    "enforcement": "hard"
  },
  "ui_hint": {"step": 0.01},
  "evidence": {"accepted_values": [0.5, 1.0]},
  "default_mode": "omit"
}
```

`domain` contains actual declared constraints. `ui_hint.step=0.01` is only the slider increment: the adjacent input can send `0.733`. A wire-level grid must be explicitly declared using `domain.multiple_of`; that grid is anchored at zero. Legacy `domain.step` remains anchored at the declared minimum. Exclusive endpoints are supported. Numeric input and slider are not populated from evidence samples.

`evidence.accepted_values` contains historical samples. A successful request means the service accepted that request, not that a parameter affected generation, and never establishes a continuous domain, an exhaustive enum, or a fixed value. A structured error records only its specifically named parameter; timeouts, auth and rate-limit failures do not become unsupported capability claims.

`unknown` and `accepted` controls are editable. Unknown enums have suggestions plus a custom input; suggestions do not prohibit a new string value. Unknown numeric controls use a clearly labelled generic slider hint and exact input. Unknown values default to omission. Declared unsupported/fixed entries remain visible in advanced settings and cannot silently replace an explicit selection.

The request policy preserves protocol/security constraints, explicit user values/omissions, explicit advanced options, workflow hints and profile defaults. An explicit omission is a tombstone: a workflow hint cannot put the field back. Hard-domain/type/condition errors stop the request before dispatch. Observations and hints do not impose hard validation.

Changing an upstream parameter no longer silently deletes dependent choices. Conflicts are shown and must be resolved before saving. This does not invent complex conditional provider semantics: declare known conjunctions/conflicts explicitly, or retain unknown evidence.

## Catalog and endpoint identity

Bundled data lives under `resources/model_catalog/`. The initial catalog has one generic entry and six endpoint-specific entries: OpenAI GPT-4.1, DashScope Qwen hybrid, DeepSeek, Moonshot Kimi K2.5, Anthropic's OpenAI shim and Google's Gemini 2.5 OpenAI shim. Each entry contains an exact model-ID list, an exact endpoint list, official documentation references and a review date. Only listed identities match; future similarly named models fall back safely.

This is deliberately a small curated catalog, not a claim to cover every model/region/gateway. Unknown models remain usable. A third-party gateway with the same model name does not inherit the official endpoint's contract. There is no substring model-name logic in the UI or provider.

The resolver supports bounded, single-parent `extends` (up to eight levels), cycle detection, exact-match ambiguity rejection, descriptor validation and protected wire paths. It can represent provider/family/model reuse without requiring all three directory levels. Descriptor replacement is atomic; it does not deep-merge incompatible paths or domain fragments. No remote JSON is fetched automatically and no expressions/scripts are executed.

Resolution order is generic/curated catalog, scoped retained declarations, freshly cached endpoint metadata, then explicit manual overrides. Evidence is attached independently. An updated catalog does not overwrite a user's selection or claim that prior observed values define the new domain. Endpoint metadata is cached for five minutes in a bounded in-memory cache; the explicit list action refreshes it. Loading local capability configuration does not secretly perform a metadata request.

The initial catalog is intentionally conservative where documentation is incomplete. Kimi temperature remains unverified rather than misrepresenting a recommended sampling setting as a required domain. Anthropic shim parameters documented as ignored are not advertised as supported simply because the underlying native API has richer functionality. Native Messages/Responses/audio transports are not implemented by this refactor.

## Adding a model or a new scalar control

Add a JSON entry with `schema_version: 1`, `id`, optional `extends`, exact `match.endpoints/models`, and complete descriptors. Include official references and `reviewed_at`. Register no new provider or frontend model-name branch. A new parameter may be number/integer/string/boolean/enum and map to body or bounded nested `extra_body` paths. Protocol/credential fields remain protected.

For a private alias, use the model settings' **manual capability override JSON** rather than changing application code:

```json
{
  "parameters": {
    "temperature": {
      "type": "number",
      "status": "supported",
      "domain": {"minimum": 0, "maximum": 1},
      "ui_hint": {"step": 0.01}
    },
    "custom_flag": {"type": "boolean", "status": "unknown"},
    "thinking_budget": {
      "type": "integer",
      "status": "supported",
      "domain": {"minimum": 0, "maximum": 32768, "multiple_of": 1024},
      "wire_location": "extra_body",
      "wire_path": ["thinking", "budget_tokens"]
    }
  }
}
```

This example is a user declaration, not detected vendor behavior. The application assigns `source=manual`; a manual JSON cannot change the endpoint, credentials, canonical messages, tools or execution privileges. Reload the local capability configuration after editing it. Any conflicting existing explicit value remains visible for correction. Model/endpoint changes clear editor overrides to avoid reusing an alias contract elsewhere.

## Passive observation and privacy

Web `SettingsService.model_snapshot()` attaches an optional observer to the model provider. A completed ordinary request may append scoped evidence, without reissuing a request or modifying the profile's declared domain. A cancelled/incomplete stream is not recorded as accepted. Observing tool calls does not authorize or execute them; the normal tool registry and PLC validation remain authoritative. A JSON sample is not proof of strict JSON-schema enforcement.

Evidence is stored lazily in `model-observations.sqlite` beside the application's user configuration, with a 30-day TTL and at most 4,096 rows. A read does not create it. SQLite failures, lock contention or corruption do not abort or retry the original generation. Records are keyed by hashed scope and a request-combination fingerprint. Public profiles do not expose keys, prompts, raw response text, tool arguments, raw errors or header values. Free-form string control values are not recorded; strings are limited to declared enum/suggestion identifiers. Model, endpoint, credentials and relevant non-tuning context scope isolation remains enforced.

Observation is best-effort and informational. It does not rewrite global presets, automatically blacklist a parameter, relax validators or silently retry with a different request. Desktop/third-party code using a bare provider without an observer retains normal transport behavior.

## v1/v2 migration and rollback

Parsing v2 is non-mutating: old metadata/manual domains remain hard; probe samples and inferred fixed values become evidence. Probe-only dependency context is evidence, not a hard prerequisite for unrelated future values. Parsing old v1 profiles uses the same distinction. Legacy explicit omission/value selections are kept. Saving an adopted configuration writes v3; GET and local resolution do not write the config.

Before accepting/saving v3 settings, back up the user configuration file. Reverting Python/TS code alone is insufficient after saving a v3-only profile because the old parser does not understand v3. Restore the config backup as well. The separate observation database may be deleted after stopping the application; it is not an engineering project store.

This refactor does not alter PLC Core, the tool registry, GX/simulation execution policies, engineering validators or Windows launcher precedence.

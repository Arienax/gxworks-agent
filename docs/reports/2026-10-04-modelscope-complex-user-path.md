## 输入极性、应用检查与已落实修复

原始 prompt 已写“程序 NO 检查位=1，NC 检查位=0”，不能将所有错误归因为完全没解释触点。实际薄弱点是输入电平未形成绑定、否定条件仍需模型自行转成位测试，以及组合条件的可达性与同扫描优先级。双泵和分拣错误包含实际 NO/NC 反用，也包含与极性无关的计数／清状态顺序错误。

本轮已在现有入口落实以下修复，保留原始实验候选和失败：

- `application.prompts` 明确分析 `implementation_semantics` 为数组；缺失为 `[]`，单项也不改成对象。
- `plc.specification.bindings` 首次修复保留明确的 `=`、用途后 `=1`、确认标题及逗号分隔声明，拒绝把寄存器分类值、条件句或设备列表当作 I/O。相同已接受分析响应的离线回放中，保留行数从 **6 增至 37／69**；该次回放仍未恢复分组／省略分隔符，不是 69 行全自动恢复。
- `application.confirmed_generation_context` 与 `knowledge.analysis_router` 去掉固定生成说明产生的 OR，阻止小写 hour 跨行粘接相邻地址。显式编辑指令、真实 HOUR 调用与正向选定指令保留。
- `knowledge.instruction_facts` 和 `knowledge.retriever` 共用最终 token 预算，修复上述 BMOV 被挤出回归。依赖闭包保持完整，超预算保留遗漏回执。
- `plc.instruction_binding.instruction_write_footprint` 的已有类型／区域定义供规格检查使用，MUL、DMUL、DDIV、BMOV 的相邻占用设备不再因只看显式首地址而被误报缺失。未知宽度和动态区域不凭空补邻居。
- `storage.session` 对 Windows 原子替换的共享冲突有限重试，持久错误仍传播，旧文件保持至替换成功；`model_runtime.provider` 不再仅因内置 `PermissionError` 类型名误判为认证错误。真实隔离 Windows 读句柄复现得到三次共享拒绝，锁释放后约 80ms 成功替换，临时文件清理完成，模型调用为零。

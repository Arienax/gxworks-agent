# 原生诊断源码映射与两个技能的实测

日期：2026-10-02。工作树基线为 `ef0a255` 加本次已冻结的修改。环境为 Windows、Python 3.13，CompilerAdapter、Compiler_IEC、Workspace 文件版本均为 `1.635.0.1`。原生操作全部使用隔离工程副本；没有 PLC 或仿真器执行、提交、推送或发布。

## 属性测试的实际收益

按 [property-based-testing](https://github.com/trailofbits/skills/blob/master/plugins/property-based-testing/skills/property-based-testing/SKILL.md) 的生成、反例解释和非空约束方法，使用隔离的 Hypothesis `6.168.3` 测试三个性质：实例连续重命名并从新字节构造上下文；形参重命名与端口取反修改的顺序无关；有明确边框的未知记录在已知节点编辑后逐字节保留。没有向项目依赖清单添加 Hypothesis。

实际反例是先对 `in.STATE` 写入端口修改，再把 `STATE` 改成 `P_0`。原草稿的 `port_edits` 仍保留 `in.STATE`，而重新读取的接口已经是 `in.P_0`；候选生成因端口名不存在而拒绝。即使取反值为 `False` 也能重现。生成阶段出现同一失败，最终最小参数为一个形参、输入侧、`False` 和最短生成名 `P_0`；原失败、解释阶段和试验源码均保留。

[editor](../../../src/gxw/editor.py)现在按修改前后的源码形参槽更新端口修改及命名连线，两侧仍分别使用 `in.NAME`／`out.NAME`。原始接口字段保持只读，草稿预览使用修改后的上下文；缺失来源和过时端点保持拒绝。输入、输出两侧的永久回归加入现有对象模型测试，没有新增测试框架依赖。

修复后通过 300 个生成案例和 3 个显式案例，分别为连续重命名 100＋1、形参／取反顺序 100、未知字节保留 100＋2。最后补加引用边界后，受影响的形参顺序性质又通过 100 个生成案例；这次复跑与前一批重叠，不相加为新覆盖。最终 Core、编译器证据、Web、MCP 和写回测试共 313 项通过。

这批性质检查的是软件编辑及字节保留。声明形参改名不会因此获得 ST 正文引用重写或原生执行正确性的认证。未知记录是受控合成记录，也不表示任意未知原生对象已获厂商接受。

## Ghidra 的实际收益与边界

使用作者 [ghidra-cli 技能](https://github.com/akiselev/ghidra-cli/blob/v0.2.2/.claude/skills/ghidra-cli/SKILL.md)及 CLI `0.2.2`，在隔离目录准备 Ghidra `12.1.4` 与 JDK `21.0.12.1+1`，导入安装中的两个 DLL 到自有分析项目。分析项目中的调用约定、接口签名与 `EH_prolog` 元数据注释依据类型库及反汇编设置，厂商 DLL 没有修改。桥接进程已关闭，反编译、命令、失败和脚本原文保留。

CompilerAdapter 的诊断转换入口仍为 RVA `0x8e48`。通过接口表确认 `GetPOULocation` 入口为 `0x14608`、`GetPCodeRangeForDebug` 为 `0x15eb3`；后者经内部 `0x49a6` 调用 Compiler_IEC 接口偏移 `252`。

这次新增的确定边界在 Compiler_IEC RVA `0x652a`。该版本的方法不读取位置、资源、计数或返回范围参数，所有路径都返回 `E_FAIL`；内部对象指针非空时错误码为 `0x50010006`，为空时静态分支为 `0x50010004`。只读跟踪在 FX3U/FX3UC、Q03UDV、L02 的三个有效副本上，分别改变 ST／FBD 位置、行和资源，共 36 次实际调用；全部进入该方法并原样返回 `0x50010006`，计数为零、范围为空。三个工程后续公开检查仍正常完成。

因此本版本的这一接口不能作为细化源码位置的有效路径。空指针分支没有额外动态调用验证；结论不推广到其他 DLL 版本或其他接口。

工具试用也保留了限制：桥接模式拒绝内联 Java，改用保存的 Java 脚本；未解码的函数不能直接创建，先按接口表提供的入口反汇编；Windows 子进程继承输出管道会拖住等待，试验入口改为文件输出。自动反编译仍需接口类型和反汇编核对。

## FB 实例诊断模块的扩展结果

在 FX3U/FX3UC 上完成一个／两个 FB 调用、每个 FB 一处／两处直接设备写入的模块对照，再扩展到前一批成功的 55 个具体 CPU 菜单选项。保留 61 次尝试，其中 6 次为启动目录冲突。不同选项沿用先前各自的完整模块、FX 类型收窄或 FX0N 项目 FB 范围；组合菜单名称不表示分别验证了每个物理型号。

55 个选项均完成编译，检查器读取的三个资源通道与本次输出相同，并取得两条 `MODULE_FB` 的原生 ST 行位置。公开诊断转换均因 `0x2d010025` 失败；47 个在失败时已有底层 100% 进度，另 8 个仍未完成底层检查。未完成选项逐项列在[机器可读结果](../../../research/results/gxw-native-diagnostic-sources-20261002.json)，不能把已取得错误写成公开检查完成。

在 54 个选项上，同次编译的主链接表有唯一实例代码区间。将原始诊断步骤、原生 ST 行、精确任务／实例名称、原生引用和调用节点几何共同核对，得到 108 条唯一实例关联。FX3U/FX3UC 的两个调用分别落在 `165..185`、`186..206`，错误步骤 `184`、`205` 指向各实例的同一条零基源码行 3；这些数值仅属于该控制输入。

FX0N 的控制输入是例外：主链接表仅有父程序 `TASK_MATRIX.FBD_MATRIX` 的 `0..7` 段，没有独立 FB 实例段。两个错误步骤为 3、7，原生位置都指向源码行 2，而引用记录同时提供两个实例候选。本快照将两条诊断保持为未解析，不用出现顺序指定实例，也不把其他 FX 选项的映射方式套用到 FX0N。

[program_check_evidence](../../../research/program_check_evidence.py)仅关联有唯一证据的受控 ST 行。缺失位置、非空库、FBD 的粗粒度网络位置、重叠代码段、重复引用和缺少当前图形对象均保持未解析。关联成功不提升公开检查状态，也没有证明任意工程的源码／配置选择链已完整受检。原来的顶层 FBD 双输出对照仍只有两个候选节点，未取得逐条错误到节点的唯一映射。

# FBD 标签作用域编辑与 CPU 扩测

日期：2026-10-04。原生组件版本为 `1.635.0.1`，工程代码页为 936。实验使用隔离工程；没有 PLC／仿真器执行、提交或推送。工作树基线及逐选项结果见[机器可读摘要](../../../research/results/gxw-fbd-label-scope-20261004.json)。

## 完成的模块

Core 现在读取当前工程的原生编译选项，用同一作用域绑定服务处理自定义 FB 的接口、图形投影、编辑和候选写入。开启局部变量隐藏全局变量时，同名局部 FB 实例可以绑定自己的类型和端口；隐藏的全局 BOOL 声明仍保留。关闭该选项、同一作用域内重复声明或选项读取不完整时，不猜测绑定。

`update_node` 的实例改名同步修改实际绑定的局部声明；声明编辑只改写属于该声明的图形引用。候选预览与重新读取沿用当前工程字节和修改后的声明。已有单程序编辑器仍拒绝跨多个程序的全局重命名，本模块没有放宽这一边界。CPU 扩测采用隐藏全局声明的注释修改，再对局部 FB 实例做中文变长重命名。

属性测试发现并固定了一个独立反例：局部 `TIMER_A` 改名时，另一个合法标识符 `TIMER_A变` 被旧的 ASCII 边界检查误判为残留引用。修复后，带中文前缀、后缀及下划线的独立标识符保持不变。现有 Core 四个测试文件共 **524 项通过**；研究中的 100 个作用域编辑序列与 9 个无效绑定编辑通过。生成案例不计为新的原生实测。

## 原生机制证据

Ghidra 静态分析确认，`OnMemoryDataManager.ParseData` 从 `0x10010000` 编译选项标签读取低位，并写入对象的 `+0x172` 字段；构造器初始化为零。这个偏移属于内存对象，不是 `.prj` 的字节偏移。

保存工程中的选项数组位于代码页 DWORD 后的 88 字节 `SystemVariablesInfo` 记录之后，计数包含最终 `0xffffffff`，原生存储上限为 32 个 DWORD。Core 保留未解释的选项值，只解释该标签；有界但不完整的可选信息进入显式读取缺口。

静态分支与原始 `GetCompileOptionPointer`、原生前端只读跟踪以及保存冷重开的结果交叉核对。关闭选项的同名对照返回 `0x500f1055` 并拒绝编译；开启时返回 `0x500f1056` 警告，实际局部实例仍为 FB。原生 API、编译器返回值和诊断没有被替换。

## 逐 CPU 菜单选项的结果

对两个原生 CPU 表和现有原生目录 API 中发现的 **69 个 Q、L、FX 菜单选项**逐一尝试。合并选项保留完整菜单名称。本模块使用两个受控源码来源：已有 `FLOW_PORTS` 库工程，以及原生工厂创建的项目 `MODULE_FB`；跨 CPU 工厂样本仍属于同一工程族，不计为独立现实工程来源。

**55 个选项**验证了原生选项解析、局部 FB／全局 BOOL 的类型绑定、两个调用、WORD 的 IN_OUT 两侧、中文实例编辑、保存和冷重开。每个选项均核对实际工程 CPU 与原生参数 CPU 字段。检查器读取的三个资源通道与当次编译输出逐字节相同；冷重开后相同通道保持一致。

这 55 个选项的编译完成且接受，底层检查完成并拒绝预设的两次 Y1 输出。原生源码查询完成；这些结果分别记录，不能合并为“检查成功”。本模块未调用公开适配器诊断转换。

| 未验证阶段 | 菜单选项 | 实际观察 |
| --- | --- | --- |
| 工程创建 | Q2A、Q2AS1、Q3A、Q4A、Q02(H)-A、Q06H-A、Q2AS(H)、Q2AS(H)S1、Q4AR | 辅助进程在 `Inside.SetReservID` 后以 `0xc0000005` 结束，未导出工程 |
| CPU 名称设置 | FXU/FX2C | 原生名称设置失败；保留 `0x15050601` 错误 |
| 原始样本编译 | FX0S/FX0、FX1、LJ72GF15-T2、LJ72MS15 | 工程创建完成，但该模块样本被原生编译拒绝，未继续编辑和冷重开 |

这 14 个选项保持未验证；创建路径失败或单一样本被拒绝不证明原生不支持 FBD。前期工程创建、粘贴、代码页、编译选项读取和辅助程序构建失败均保留在证据中。

原生引用 API 对每个 IN_OUT 形参只返回一条 class 5 记录，不能用其 attribute 数值推导图形端点数量。两个图形端点由保存的源图分别验证，D30／D40 的原生物理写端引用另行核对；本模块不据此推断运行时写回语义。

## FX0N 实例诊断的差异

54 个已验证选项的原生位置直接指向 FBD 调用程序。FX0N 则将此控制中的项目 FB 内联，两个诊断都指向 `MODULE_FB` 的零基第 0 行。原始 `ChangePToILcode` 和 `GetStepSize` 完整读取同次 71 字节代码，两个 `OUT Y1` 分别位于步骤 1 和 3；此证据绑定 FX0N、CPU 514、`ECCodeGeneratorFX2.dll 15.31`。

原始 `GetPCodeRange` 接受当前完整实例路径，将 `FBD_MATRIX.混合范围实例_STAGE_A` 映射到 `[0,2)`，将 `FBD_MATRIX.TIMER_B` 映射到 `[2,4)`。结合当前原生调用引用与图形边框，两条诊断分别唯一定位到两个调用节点。这与同次调试记录独立一致，无需按出现顺序指定实例，也不借用其他 FX 型号的代码生成方式。

复用原有 ST 实例关联器后，FX0N 范围性质通过 200 个一致变体、36 个矛盾输入和 2 个重叠范围控制；包含既有 Q03UDV 嵌套调用的联合回归也通过。失败接口、缺失响应、资源不一致、范围重叠或调用引用缺失时保持未解析，旧链接缓存不能替代原始范围响应。唯一关联不提升公开检查状态。

# FX3U instruction contract coverage and batch promotion

## What the audit measures

`tools/audit_fx3u_contracts.py` audits **every literal opcode form currently
admitted for FX3U generation**, including already-catalogued D/P variants. This
is a denominator of 282 forms, not a claim to implement every vendor instruction
or every hardware option. A separate list reports native-manual forms outside
that generation catalogue. Opcode admission and the existing quarantine are
unchanged.

The legacy `contract_level=full` field was a metadata classification, not proof
that every constraint had been verified. Core now reports independent dimensions:
CPU/hardware applicability, arity, native operand order, operand roles/types/device classes, literal form
identity, execution form, operation width, execution conditions, completion
ownership, and numeric/memory boundaries. Legacy annotations are labelled
`declared_unverified`; missing facts remain `unresolved`. A corroborated
signature is **not** a complete behavioral or hardware contract.

## Evidence method

The source database is opened read-only. Source identities, revisions and PDF
SHA-256 values must agree with `resources/knowledge/sources.json`.

1. Read the complete original native `Instruction format` and `Set data` page
   geometry in JY997D16601R, not the partial `instructions.operands_json` field.
   Require one native operand symbol per complete data row. Missing symbols,
   conflicting native definitions and conditional/composite cells do not pass.
   Where the table detector failed, the bounded original set-data region is
   used; that alone is never sufficient to promote.
2. Require independent explicit ST call syntax from its own instruction section
   in JY997D34701M. Remove only EN; require its complete argument count to agree
   with the native signature. An example belonging to another instruction is
   not corroboration. A documented sibling is accepted only if both literal
   forms occur in the same native mnemonic table.
3. Preserve **native** symbol order. For example WSFL's native order is
   `S, D, N1, N2`; the ST wrapper orders `s, n1, n2, d` after EN. It would be
   incorrect to translate the ST ordering directly into ladder operand order.
4. Identify executable forms from the native **Mnemonic columns**, not the
   illustrated instruction icon. A template icon can display a base name that
   is not an executable native form. Execution form (continuous/pulse) and
   operation width (16/32) are promoted only when the same literal form also
   agrees in both source pages.
5. Reject proposed promotions that contradict an existing arity. Do not promote
   types, writable ranges, roles or completion ownership merely because arity
   agrees. Those require their own evidence interpretation and validation.

The generated ledger records both manual identities, 1-based PDF pages, exact
native order and evidence hashes. It contains metadata, not copied manual pages
or live user traces. It can be regenerated byte-for-byte. Database content and
reviewed signatures are never rewritten by the production runtime.

## Audited baseline and resulting coverage

| Dimension | Result |
| --- | ---: |
| Generation forms audited | 282 |
| Corroborated native signatures/form identities | 227 |
| Existing opcode-only forms gaining a signature | 84 |
| Exact arity coverage before → after | 11 → 230 |
| Corroborated continuous/pulse forms | 219 |
| Corroborated 16/32-bit operation widths | 216 |
| Not promoted by this method | 55 |
| Claimed fully verified behavioral contracts | 0 |

The 230 exact arities include three pre-existing contracts preserved without a
new cross-manual promotion. Nonpromotion is not proof of an invalid opcode.

Nine forms lack independent complete-call corroboration: BK+, FOR, IRET, IST,
LIMIT, NEXT, RBFM, REFF, SRET. Another 46 lack a complete unambiguous native
signature/form under this method: ABS, ACOS, ADPRW, ASIN, ATAN, CALL, CJ, COS,
DEG, DRAMP, DSORT, EADD, EBCD, EBIN, ECMP, EDIV, EMOV, EMUL, ENEG, ESQR,
ESTR, ESUB, EVAL, EXP, EZCP, HCMOV, HSCR, HSCS, HSCT, HSZ, LOG10, LOGE,
MC, MCR, MIDR, MIDW, MODBUS, MODRW, NOP, RAD, RST, SET, SIN, SORT2, TAN,
TBL. The machine-readable report includes individual reasons, original arities,
candidate pages and every dimension's before/after state. Existing SET/RST/BK+
checks are not removed because these entries were not promoted again.

## Shared runtime consumers

`InstructionRegistry.resolve(opcode, cpu="FX3U")` selects a CPU-scoped,
literal-form override. `cpu=None` retains the model-neutral import/IR view;
FX5U does not inherit FX3U-only evidence. Existing read/write annotations and
admitted opcodes are unchanged. Signature corroboration does not verify conditional CPU/hardware availability.
Unknown vendor instructions can still be preserved by import paths; they are not promoted or interpreted speculatively.

The existing generic APP_INSTR validator consumes the CPU-scoped arity. Field
repair candidate filtering consumes the same view; no semantic rewrite/retry
policy is added. Analysis and the shared selected-instruction capability prompt
use `describe_contract()`, including explicit verified/unverified fields.
Compact Agent B and ladder_v1/MCP use the same selected snapshot. There is no
282-instruction prompt dump and no new opcode-specific prompt recipe.

The legacy JSON schema still describes representation and allowed opcode
identity. It does not itself prove instruction semantics. The shared Core
validator enforces the promoted arities; source text retrieval remains separate
and is still required for facts not captured by the signature contract.

## Reproduce and review

Run from the repository root with the existing Python dependencies and checked
out LFS knowledge index:

```powershell
python tools/audit_fx3u_contracts.py --report fx3u-contract-audit.json
python tools/audit_fx3u_contracts.py --check
python -m pytest -q tests/test_instruction_contract_alignment.py tests/test_instruction_registry.py
```

After changing reviewed sources or the auditor, inspect the full report and use
`--promote` to regenerate only corroborated signature metadata. `--check` fails
if the checked-in ledger drifts. It is exercised in the existing instruction
alignment suite and its existing Windows/full-suite workflows, not a new
production confirmation gate or a separate permanent CI workflow.

Regression coverage includes every promoted literal form's wrong arity,
representative valid native operands across instruction families, native/ST
ordering, incomplete/conflicting evidence, malformed ledger atomicity, CPU
isolation and compact/MCP snapshot equality. No live model, GX compilation,
PLC operation or performance improvement is implied by passing these tests.
